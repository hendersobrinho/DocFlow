# 10. Banco De Dados

## 10.0 Servidor e conexao

O sistema usa **PostgreSQL** (versao 13 ou superior). O banco precisa existir antes do
primeiro acesso; as tabelas, indices e dados iniciais sao criados automaticamente por
`initialize_schema()` a cada abertura (de forma idempotente e serializada por advisory lock,
para varias estacoes poderem abrir ao mesmo tempo).

Requisitos no servidor:

- a extensao `citext` disponivel (vem no pacote `contrib`, padrao nas instalacoes do PostgreSQL);
  o usuario do sistema precisa poder cria-la (`CREATE EXTENSION citext`) ou ela ja deve existir
- o usuario de conexao deve ser dono do banco (ou ter permissao de criar tabelas no schema `public`)

Exemplo de preparacao:

```sql
CREATE ROLE docflow LOGIN PASSWORD 'troque-esta-senha';
CREATE DATABASE docflow OWNER docflow;
```

Como o DocFlow encontra o banco:

1. variavel de ambiente `DOCFLOW_DATABASE_URL`, se definida (URL `postgresql://usuario:senha@host:5432/banco`
   ou formato `chave=valor` do libpq)
2. senao, a conexao salva pela tela **Banco de dados** (servidor, porta, banco, usuario, senha e SSL),
   guardada no `config.json` do perfil do usuario; no Windows a senha fica protegida com DPAPI

Detalhes da implementacao (`documentos_empresa_app/database/connection.py`):

- driver `psycopg` 3; uma conexao por instancia, reaproveitada e protegida por `RLock`
- blocos `connect()` aninhados participam da mesma transacao (commit/rollback no bloco mais externo)
- os repositorios continuam escrevendo SQL com placeholders `?`; a conexao converte para `%s`
- escrita que falha dentro de um bloco maior e isolada por `SAVEPOINT`, para o service poder tratar
  o `IntegrityError` e seguir usando a transacao (mesmo comportamento que o SQLite tinha)
- datas continuam gravadas como `TEXT` no formato `YYYY-MM-DD HH:MM:SS` (UTC) pela funcao
  `docflow_utc_now()`, o mesmo formato que o `CURRENT_TIMESTAMP` do SQLite gerava

Convencoes de tipos usadas nas tabelas abaixo:

- `PK` = `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `CITEXT` = texto que compara sem diferenciar maiusculas/minusculas (substitui o `COLLATE NOCASE` do SQLite,
  inclusive em `UNIQUE`, `=`, `ORDER BY` e `LIKE`)

## 10.1 Tabelas existentes

### `empresas`

| Campo | Tipo | Regras |
|---|---|---|
| `id` | INTEGER | PK |
| `codigo_empresa` | INTEGER | obrigatorio, unico |
| `nome_empresa` | CITEXT | obrigatorio |
| `meios_recebimento` | TEXT | legado/compatibilidade, nao usado como regra principal atual |
| `email_contato` | TEXT | opcional |
| `nome_contato` | TEXT | opcional |
| `observacao` | TEXT | opcional, maximo 255 caracteres |
| `diretorio_documentos` | TEXT | opcional |
| `ativa` | INTEGER | default `1`, check `0/1` |

Observacao:

- o campo `meios_recebimento` foi mantido para compatibilidade com bancos antigos
- a regra atual do sistema usa meios de recebimento por documento

### `tipos_documento`

| Campo | Tipo | Regras |
|---|---|---|
| `id` | INTEGER | PK |
| `nome_tipo` | CITEXT | obrigatorio, unico |
| `regra_ocorrencia` | TEXT | obrigatorio, `mensal`, `trimestral` ou `anual_janeiro` |

Uso:

- agrupar documentos
- alimentar seletores de tipo
- definir em quais meses aquele tipo deve ser cobrado

### `meios_recebimento_sistema`

| Campo | Tipo | Regras |
|---|---|---|
| `id` | INTEGER | PK |
| `nome_meio` | CITEXT | obrigatorio, unico |

Uso:

- alimentar o componente de selecao de meios
- permitir renomear/remover meios globais sem apagar historico dos documentos

### `documentos_empresa`

| Campo | Tipo | Regras |
|---|---|---|
| `id` | INTEGER | PK |
| `empresa_id` | INTEGER | FK para `empresas`, `ON DELETE CASCADE` |
| `tipo_documento_id` | INTEGER | FK para `tipos_documento`, `ON DELETE RESTRICT` |
| `meios_recebimento` | TEXT | opcional |
| `nome_documento` | CITEXT | obrigatorio; curto, sem repetir o tipo (ex: tipo Extratos CC, nome Banco do Brasil) |
| `observacao` | TEXT | opcional, ate 500 caracteres (numero da conta, produto, contrato...) |

Restricao importante:

- `UNIQUE (empresa_id, tipo_documento_id, nome_documento)`

### `periodos`

| Campo | Tipo | Regras |
|---|---|---|
| `id` | INTEGER | PK |
| `ano` | INTEGER | obrigatorio |
| `mes` | INTEGER | obrigatorio, `CHECK 1..12` |

Restricao:

- `UNIQUE (ano, mes)`

### `status_documento_mensal`

| Campo | Tipo | Regras |
|---|---|---|
| `id` | INTEGER | PK |
| `documento_empresa_id` | INTEGER | FK para `documentos_empresa`, `ON DELETE CASCADE` |
| `periodo_id` | INTEGER | FK para `periodos`, `ON DELETE CASCADE` |
| `status` | TEXT | `NULL`, `Recebido`, `Pendente` ou `Encerrado` |
| `updated_by_user_id` | INTEGER | opcional, usuario que fez a ultima alteracao |
| `updated_at` | TEXT | timestamp da ultima alteracao |

Observacao importante:

- `Nao cobrar` nao e persistido nessa tabela
- esse valor e calculado dinamicamente pela regra de ocorrencia do tipo

Restricao:

- `UNIQUE (documento_empresa_id, periodo_id)`

### Campos de recebimento em `empresas`

| Campo | Tipo | Regras |
|---|---|---|
| `canais_recebimento` | TEXT | opcional, lista separada por virgula (ex: `Email, Onvio`) |
| `emails_origem_documentos` | TEXT | opcional, emails de onde os documentos chegam |
| `instrucoes_busca` | TEXT | opcional, texto livre de onde/como procurar os documentos |

### `cobrancas`

Cada registro e um contato feito com a empresa cobrando documentos.

| Campo | Tipo | Regras |
|---|---|---|
| `id` | INTEGER | PK |
| `empresa_id` | INTEGER | FK para `empresas`, `ON DELETE CASCADE` |
| `canal` | TEXT | obrigatorio (Email, WhatsApp, Onvio, Telefone...) |
| `destinatario`, `assunto`, `mensagem`, `observacao` | TEXT | opcionais |
| `realizada_em` | TEXT | default `docflow_utc_now()` |
| `usuario_id` | INTEGER | FK para `usuarios`, `ON DELETE SET NULL` |

### `cobranca_itens`

Documentos e competencias cobrados em cada contato.

| Campo | Tipo | Regras |
|---|---|---|
| `cobranca_id` | INTEGER | FK para `cobrancas`, `ON DELETE CASCADE` |
| `documento_empresa_id` | INTEGER | FK para `documentos_empresa`, `ON DELETE CASCADE` |
| `periodo_id` | INTEGER | FK para `periodos`, `ON DELETE CASCADE` |
| `sequencia` | INTEGER | 1 = primeira cobranca daquele documento na competencia; 2+ = recobranca |

### `verificacoes` e `verificacao_itens`

Relatorio de cada conferencia nos canais da empresa: `verificacoes` guarda onde se procurou
(`fontes`), um `resumo`, quem/quando e a `rodada_id` (opcional). `verificacao_itens` guarda, por
documento e competencia:

| Campo | Tipo | Regras |
|---|---|---|
| `resultado` | TEXT | `recebido`, `documento_com_problema`, `nao_encontrado` ou `verificacao_falhou` |
| `motivo` | TEXT | motivo do problema (`documento_errado`, `competencia_errada`, `ilegivel_ou_incompleto`, `empresa_errada`, `outro`) ou da falha |
| `baixa_feita` | INTEGER | 1 quando o item `recebido` foi marcado como `Recebido` em `status_documento_mensal` |
| `baixa_erro` | TEXT | por que a baixa nao foi feita |
| `encontrado`, `onde`, `observacao` | | `encontrado` (0/1) e mantido por compatibilidade |

### `situacoes_cobranca` e `situacao_eventos`

Onde cada documento esta no fluxo de cobranca, por competencia (unico por
`documento_empresa_id` + `periodo_id`): `situacao` (`a_verificar`, `recebido`,
`documento_com_problema`, `nao_encontrado`, `verificacao_falhou`, `cobrado_aguardando`,
`promessa_envio`, `precisa_pessoa`), `motivo`, `detalhe`, `aguardar_ate` (data da promessa),
quem/quando e `rodada_id`. Cada mudanca gera uma linha em `situacao_eventos`
(`situacao_anterior` -> `situacao_nova`), que e o caminho mostrado na Ficha e em Precisa de
atencao.

### `rodadas` e `rodada_ocorrencias`

Cada passada do Claude: `origem`, `iniciada_em`, `finalizada_em`, `status` (`em_andamento`,
`concluida`, `concluida_com_falhas`) e `resumo`. Uma rodada `em_andamento` ha mais de 6 horas e
mostrada como interrompida. `rodada_ocorrencias` guarda falhas, avisos e informacoes da rodada
(`tipo`, `mensagem`, `empresa_id` opcional).

### Regras do acompanhamento

`configuracoes_cobranca` tambem guarda `dias_entre_cobrancas` (0 a 60, padrao 3),
`max_recobrancas` (0 a 20, padrao 3) e `problema_vai_para_pessoa` (0/1, padrao 1), usados pelo
planejador `CobrancaService.proximas_acoes`.

## 10.2 Relacionamentos

- `empresas 1:N documentos_empresa`
- `tipos_documento 1:N documentos_empresa`
- `usuarios 1:N sessoes_lembradas`
- `documentos_empresa 1:N status_documento_mensal`
- `periodos 1:N status_documento_mensal`
- `usuarios 1:N logs`
- `empresas 1:N cobrancas 1:N cobranca_itens N:1 documentos_empresa / periodos`
- `empresas 1:N verificacoes 1:N verificacao_itens N:1 documentos_empresa / periodos`
- `documentos_empresa 1:N situacoes_cobranca N:1 periodos` (uma por competencia) e `1:N situacao_eventos`
- `rodadas 1:N rodada_ocorrencias`; `rodadas 1:N verificacoes / cobrancas / situacao_eventos` (`ON DELETE SET NULL`)

## 10.3 Integridade e comportamento de exclusao

- excluir empresa remove documentos e status mensais associados
- excluir documento remove status mensais associados
- excluir periodo remove status mensais associados
- excluir tipo e bloqueado se houver documento usando o tipo
- excluir usuario nao apaga log; o `usuario_id` pode ficar `NULL`

## 10.4 Backup, restauracao e migracao do SQLite

- o backup (`DatabaseMaintenanceService`) e logico: todas as tabelas sao lidas num mesmo snapshot
  (`REPEATABLE READ`) e gravadas como JSON compactado com gzip, extensao `.dfbak`; com senha
  configurada, o arquivo e criptografado (Fernet/AES, chave via PBKDF2) antes de ir para o disco
- nao depende do `pg_dump`, entao funciona em qualquer estacao com o DocFlow instalado
- a restauracao apaga os dados atuais (`TRUNCATE ... RESTART IDENTITY`), insere os do backup
  respeitando a ordem das chaves estrangeiras, reposiciona as sequencias e reaplica as normalizacoes
- **migracao de instalacoes antigas:** a restauracao tambem aceita o arquivo `.db` do SQLite usado
  pelas versoes anteriores (e os backups `.db` gerados por elas, inclusive criptografados). Colunas
  que nao existiam no banco antigo recebem o valor padrao; os valores sao convertidos para o tipo da
  coluna de destino. Na primeira abertura depois da atualizacao, se o `config.json` ainda tiver o
  `db_path` antigo, o sistema mostra o caminho do arquivo para importar

Normalizacoes que rodam a cada abertura e apos restaurar (`apply_data_normalizations`):

- copia `meios_recebimento` legado da empresa para documentos que ainda nao tenham esse dado
- padroniza `regra_ocorrencia` e os meios de recebimento
- preenche `updated_at` vazio nos status e os metadados de empresa/periodo dos logs antigos
